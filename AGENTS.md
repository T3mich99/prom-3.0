# UG-OPT → Prom: правила роботи Codex

## На початку кожного завдання

- Працюй у корені цього репозиторію. Прочитай README.md, docs/OPERATOR_WORKFLOW.md,
  config/photo-styles.json, config/google-drive-media.json, config/category-workflow.json, docs/CODEX_CATEGORY_EXECUTION.md і docs/CATEGORY_PRODUCTION_CONTRACT.md.
- Перевір git status, гілку і commit. Не скидай зміни користувача. ZIP без .git
  не є синхронізованим GitHub checkout; повідомляй про це чесно.
- Для категорії запускай `npm run category -- --request <json> --result <json>`.
  `npm run production` — попередній FULL_CATALOG/EXPLICIT_CATEGORIES маршрут.
  Не підмінюй процес датованими root-скриптами, excel-work або одноразовим генератором.
  Якщо крок відсутній, виправ канонічний код і перевір його.
- Використовуй задану категорію. Якщо дана лише назва, знайди точну URL категорії
  на UG-OPT. Неоднозначність уточнюй; не вибирай іншу категорію самостійно.

## Короткі запити — повне виконання

- «Зроби 100 товарів із категорії X» — достатнє завдання. Сам знайди точну URL,
  створи request із targetCount: 100 та виконай повний маршрут до XLSX. Не вимагай
  повторних вказівок «перевір дублікати», «зроби фото», «заповни опис» або «продовжуй».
- Каталог для звірки бери з config/category-workflow.json. Він уже вказує на
  наданий Excel. Явно наданий новий каталог підключай через export.inputPath;
  після успішної перевірки CLI запам'ятовує шлях. Не перепитуй його кожну партію.
- CLI перевіряє весь реєстр ДО відбору кількості. Не витрачай генерацію на дублікати.
  Модель не публікуй; код товару використовуй для обліку і відповідної колонки Excel.
- Для нової партії використовуй нові request/result шляхи; для продовження — попередні.
  Перед новою партією перевір незавершені запуски. Не запускай другу партію тієї самої
  категорії поверх незавершеної. Після експорту реєстр зберігає резервування кодів.
- Підсумок знайдено/виключено/відібрано повідомляй як статус і продовжуй без
  проміжного погодження. При нестачі нових товарів підготуй доступні й назви точний
  дефіцит; partialWorkbookReady не видавай за виконаний targetCount.
- Завантаження, контент, ціни, фото, QA та Excel — стандартні етапи цього запиту.
  Якщо змінений каталог потребує reconciliation, виконай звірку й збережи старі
  резервування. Не видаляй базу заради обходу перевірки; невирішений конфлікт —
  фактичне блокування. Автоматичної синхронізації з магазином Prom немає.

## Виконавець і межа завершення

- Виконавець operatorTasks — сам Codex. Не проси користувача вручну писати контент,
  промпти або переносити колонки, якщо відповідні інструменти доступні.
- Типовий маршрут — інструменти поточної Codex-сесії через вхід ChatGPT, включно
  з вбудованою генерацією зображень. Не переходь на оплачуваний API, не купуй кредити
  й не запускай зовнішній платний сервіс без прямої вказівки користувача.
- Збери всі сторінки заданої категорії. Якщо користувач задав кількість, запиши
  targetCount і підготуй саме стільки НОВИХ допустимих товарів після звірки реєстру.
  Без кількості обробляй усю нову допустиму категорію. Наявні й зарезервовані не дублюй.
- Виконуй завдання, записуй артефакти в request і повторюй category до готовності.
  WAITING_FOR_OPERATOR означає роботу для тебе, а не привід завершити відповідь.
- Зупиняйся лише на фактичному блокуванні: інструмент/доступ недоступний, ліміт,
  відсутні факти або неоднозначність. Збережи прогрес і точну причину. Не обходь ліміти.
- Готова категорія потребує completion.finalWorkbookReady=true і
  reservationStatus=COMPLETE; список виключених SKU покажи окремо.
  Порожній або частковий XLSX не називай завершеною категорією.

## Дані та Excel

- Еталон: templates/prom-reference.xlsx; схема й SHA-256 поруч.
- Новий імпорт створюй через exportPromDeltaWorkbook: лише нова партія, без 966
  старих рядків. Зберігай 108 колонок, 19 повторюваних блоків характеристик і аркуш груп.
- Не перетворюй повторювані заголовки характеристик на словник, що втрачає колонки.
- Перевіряй supplier SKU і реєстр Prom. Не вигадуй коди, категорії чи характеристики.
  Для НОВИХ товарів Prom-assigned ID порожні; наявні товари не переписуй цим маршрутом.
- Ціни: чинна category ROI curve у src/pricing/market-pricing.mjs. Не підставляй старі
  30%, ×1.8 або єдині 90% з переписки. Нову явну вказівку користувача реалізуй разом
  із документацією та тестами політики.
- Метадані виробника й країни для фізичного Excel: підтверджені значення UG-OPT або
  вже підтверджені значення під час підготовки зберігай без змін. Якщо поле порожнє
  перед канонічним експортом, експортер обов'язково підставляє `Виробник=AND` та
  `Країна_виробник=Китай`. Це правило стосується лише фізичних колонок Excel і не
  додає непідтверджених фактів до sourceFacts, назв, описів, ключових слів чи фото.
  Перевіряй обидва поля в кожному майбутньому XLSX через канонічний маршрут.
- Модель не вказуй у назві, описі (зокрема у блоці характеристик опису) та на фото.
  Справжній бренд зберігай. Вихідну модель залишай у sourceFacts для ідентифікації.
- Назви й описи — конкретні, з підтвердженим брендом і характеристиками. Без
  «ймовірно має», «тип уточнюйте», вигаданих функцій і секції «Комплектація».
  Назва має прямо пояснювати, що це за товар і для чого він призначений, якщо
  призначення підтверджене джерелом. Обірвані конструкції на кшталт «для: точний
  вибір» або назви без уточнення призначення не приймай і переробляй до Excel.
  Ключі мають відповідати фактичному типу товару. Поважай окремі UA/RU поля й commercial-prom-v2.
  Для кожної мови виконуй обов'язкову редакторську перевірку
  `commercial-editorial-v1`: правильна граматика, природні словосполучення,
  чиста мова без кальок і змішування UA/RU, конкретний вступ із користю для
  покупця, жива лексика та власна подача саме цього товару. Шаблонний або
  «водянистий» текст, складські позначки на кшталт «шт», порожні слогани,
  повторювані вступи й текст, який просто досягнув довжини, не є готовим.
  Перевіряй назву й опис після генерації, а при будь-якому редакторському
  дефекті запускай CONTENT_REWORK до `READY`; не передавай такий текст у фото
  або Excel. Формальна перевірка не доводить гарантовану конверсію, але
  редакторський gate обов'язково відсікає об'єктивні мовні й шаблонні дефекти.
  Опис кожного товару будуй у фіксованому продажному порядку: причина купити й
  реальний сценарій, конкретні переваги з підтверджених фактів, кому підійде,
  повні характеристики та коротке практичне завершення. Адаптуй аргумент до
  категорії: для бандажа пояснюй підтримку й посадку, для тренажера — сценарій
  занять, для б'юті-інструмента — процедуру, для масажера — зону й формат, для
  побутового товару — конкретну домашню задачу. Сухий вступ «товар призначений
  для», водянисті фрази, повтори між товарами й текст, який лише набрав потрібну
  довжину, не приймай.

## Фото

- Канонічні правила: docs/PHOTO_PRODUCTION_CONTRACT.md, config/photo-styles.json,
  src/photos/*.mjs. PHOTO-MASTER-SPEC.md є вказівником, а не окремою політикою.
- П'ять окремих файлів: hero, usage, benefits, feature, final. Ціль 1280×1280.
  План → генерація → перевірка байтів і візуальний огляд → публікація/перевірка URL → Excel.
- Схвалений глобальний стиль (чинна версія у config/photo-styles.json): references/photos/global/commercial-infographic-approved-2026-09-17.png.
  Відкрий його перед першою генерацією. Це стиль інфографіки, а не шаблон сцени чи
  джерело цифр, брендів і характеристик інших товарів.
- Виконай PHOTO_ART_DIRECTION: збережи photoCreativeBrief для конкретного SKU.
  Усі п'ять кадрів мають різні сцени, композиції, смисли й макети тексту; кожен
  товар має власну концепцію. Колір фону й заголовок самі по собі не є унікальністю.
  Фото 1–4 — інфографіка, 5 — предметне без тексту та піктограм.
- Порівнюй галерею з іншими товарами й runtime/photo-creative-history.json.
  Точні повтори задумів блокує код; семантичні й візуальні повтори перевіряй сам.
- Використовуй готові operatorTasks[].input.photos[].prompt і styleProfile. Передай
  справжні source references та style references до доступного ImageGen/provider;
  текстовий шлях сам собою не передає зображення.
- Джерело визначає точний товар, еталон визначає стиль. Зберігай реальний бренд,
  прибирай модель/SKU/артикул з фото. Жодних чорних хмар, ореолів, важких віньєток
  та брудного контуру. Чорний товар залишається чорним. Тінь — делікатна й локальна.
- Не вигадуй невидиму геометрію заради ракурсу: використай інший справжній референс
  або безпечний кроп/композицію. Не перезаписуй схвалені файли.
- Не став checklist, зокрема noDarkHalos, sceneDistinct, layoutDistinct, productSpecificDesign, у true без огляду фактичного зображення.
  Кожен кадр має бути повністю непрозорим до чотирьох країв і кутів; чорний контур,
  чорні кути, прозорий/вирізаний край, темна віньєтка або ореол — підстава для
  відбракування та повторної генерації до внесення фото в Excel.
  PNG PASS не доводить правильності тексту або комерційної якості.
- Якщо генерація/хостинг недоступні, збережи стан і назви блокування. Не підставляй
  старі фото, фіктивні файли чи вигадані URL замість готового результату.

## Після затвердження коригування

1. Визнач область: productKey, точна URL категорії або global. Не поширюй локальне
   схвалення автоматично на всі категорії.
2. Збережи схвалені зображення у references/photos/<scope>/ і зареєструй path/reason
   у config/photo-styles.json. Не вигадуй схвалення, якщо приклад ще не затверджено.
3. Онови global/families/categories/products, збільш version, додай запис changes
   з конкретною вказівкою користувача. Усунь суперечливі старі правила.
4. Створи новий план і перевір фото. Не підмінюй fingerprint вручну. Після глобальної
   зміни всі плани проходять перевірку заново.
5. Запусти релевантні тести. За наявності авторизації зроби commit/push або PR у погоджену
   гілку. Інакше підготуй patch/ZIP і скажи, що GitHub ще не оновлено. Усне «запам'ятав»
   не є збереженням правила.

## Звіт

Покажи фактичні статуси, кількість товарів, шлях Excel, версію стилю, SHA шаблону,
виконані перевірки та блокування. WAITING_FOR_OPERATOR не є готовою партією.
Створення XLSX не є імпортом у Prom; без запиту не імпортуй у магазин.

## Постачальник і Google Drive

- Джерело: https://ug-opt.in.ua/ua/. Головна сторінка не задає конкретну категорію.
- Налаштування папок у config/google-drive-media.json. Корінь Prom 2.0 наданий
  користувачем, PRODUCT IMAGES та FINAL EXCEL підтверджені читанням Google Drive.
- Завантажуй товарні фото в PRODUCT IMAGES через підключений Google Drive.
  Генеруй їх лише у тимчасовій папці конкретного productKey і не зберігай локальні
  байти після завершення перевіреного Drive-публікування.
- Схвалений референс також збережений у STYLE REFERENCES; він не є товарним фото.
- Після завантаження виконай category:media з publication та approvedMedia:
  команда перевіряє прямі URL без авторизації, тип зображення й відповідність SHA
  локальним файлам. Після успішної перевірки всіх п'яти позицій вона видаляє лише
  ці п'ять точно зіставлених локальних файлів і повертає cleanup.status=
  `LOCAL_FILES_REMOVED`. Публікуй у Excel тільки після цього статусу; у стані
  залишаються шляхи та хеші як provenance, але не байти фотографій.
- Не змішуй товари: кожен файл зв'язаний одночасно з productKey, supplier SKU,
  індексом 1–5, канонічною роллю, SHA-256 і власним Drive fileId. Заборонене
  повторне використання одного локального шляху в п'яти ролях або між товарами.
- Для Excel прийнятна лише мережево підтверджена форма
  `https://lh3.googleusercontent.com/d/<fileId>=w1280` із verification від
  `category:media` (`PUBLIC_IMAGE_SHA256_VERIFIED`). `drive.google.com/uc?export=view`,
  `/file/.../view`, авторизоване читання через Drive або `LOCAL_ONLY` не є
  публічною медіа-публікацією; такий товар блокується до експорту.
- Не змінюй права батьківських папок і не перезаписуй старі зображення через збіг імен.
  Upload успішний не означає, що адреса придатна для імпорту Prom.
