# Робочий процес для Codex

## 1. Відкрити правильний проєкт

Відкрий папку з AGENTS.md та package.json. У Git checkout перевір git status,
branch і log; звір віддалені зміни, не перезаписуючи локальну роботу. У ZIP немає
історії оригінального GitHub. Після перевірки перенеси зміни у свою робочу гілку
та зроби commit/push. Локальна зміна без push не оновить іншу копію репозиторію.

## 2. Запит категорії

Скопіюй examples/category-request.example.json у requests/category.json і постав
точну URL категорії користувача. Не запускай приклад із REPLACE_WITH_EXACT_CATEGORY_PATH.
Ім'я категорії є поясненням, URL визначає область збору. Задану користувачем кількість передай як targetCount; без неї не додавай ліміт.

```powershell
npm ci
npm run category -- --request requests/category.json --result outputs/category-result.json
```

Команда один раз зберігає master template і реєстр у runtime/prom-category.sqlite.
Наступні запуски бачать наявні та зарезервовані товари. Інший Excel потребує явного
reconcile через наявний prom-catalog-bootstrap; не видаляй базу, щоб обійти перевірку.
CLI запускає лише один категорійний процес за раз у цій копії репозиторію.

## 3. Виконати завдання

Результат — JSON зі status, products, operatorTasks і export. Codex виконує кожне
актуальне завдання засобами, доступними у його середовищі. Це не безперервний фоновий
AI-сервіс. Для продовження збережи фактичні артефакти у productInputs за productKey,
не видаляючи вже прийняті поля, і повтори ту саму команду.

- Перевір сторінку точного SKU: вартість, наявність, зображення, бренд, функції.
  Передай sourceFacts, sourceText і sourceImages. Назва каталогу сама по собі не
  підтверджує всі характеристики.
- CONTENT_GENERATION/CONTENT_REWORK: дотримуйся схеми завдання та commercial-prom-v2.
  Джерела і підтверджені факти — обов'язкові. Не став «READY» власноруч.
- PHOTO_ART_DIRECTION: створи окремий photoCreativeBrief за схемою завдання.
  Не копіюй сцени чи макети з іншого SKU. Запиши його у productInputs й повтори
  команду, щоб одержати актуальні промпти.
- PHOTO_GENERATION/PHOTO_REWORK: використай вже сформовані prompt, text,
  visualDirection.styleProfile та точні sourceImageRefs. Якщо немає інструмента
  генерації — явно вкажи блокування, не створюй фіктивні PNG.
- Передай джерела і затверджені еталони як реальні вхідні зображення. Отримай п'ять
  окремих результатів; перевір PNG, точність товару, бренд, український текст,
  відмінність сцен, макетів, товарних концепцій та noDarkHalos. Checklist заповнюється після огляду.
- Завантаж перевірені файли на доступний публічний хостинг. Google Drive bridge
  зберігає відбитки файлів і перевіряє надані URL через probe. Сам delta-експортер
  перевіряє структуру HTTPS URL; він не доводить їхню мережеву доступність.
- Передай publishableMedia, що відповідає саме approvedMedia цього товару.

Старий план без styleProfile треба перебудувати. Зміна style profile або байтів
еталону змінює fingerprint і блокує повторне використання старого плану як актуального.

## 4. Метадані Prom

У productInputs[productKey].resolvedMetadata передавай підтримувані канонічні поля
на кшталт productCode, unit, currency, availability, categoryId, categoryName,
manufacturer. Ціну й фото туди не записуй: вони належать валідованим артефактам.

Для фізичних полів, яких немає у канонічному словнику, використай
productInputs[productKey].promFields, зокрема Номер_групи та Посилання_підрозділу.
Бери їх із перевіреного зіставлення з Prom. Не плутай групу магазину з категорією
маркетплейсу і не вгадуй їхні ID. Порожні обов'язкові поля блокують експорт.
promFields не може переписувати ціну, код, фото або затверджений основний контент.

Для запиту з targetCount фінальний файл потребує готовності всіх відібраних товарів
і досягнення запитаної кількості; невідібрані кандидати не блокують цю партію.
Без targetCount потрібна готовність усієї нової допустимої категорії, без невалідних
кандидатів. В обох випадках не має бути невирішених завдань, а всі фото мають бути
опубліковані й перевірені. При нестачі нових товарів можливий лише чесно позначений
частковий файл із shortfall. Для XLSX обирай новий шлях: CLI забороняє перезапис
початкового каталогу, request та вже наявних файлів.
Він містить 108 колонок еталону, 19 слотів характеристик і незмінені групи. 966 старих
товарів не копіюються. Prom-assigned ID нових позицій залишаються порожніми.
Оновлення вже існуючих товарів є окремим завданням; цей CLI їх пропускає.

## 5. Коригування, які не губляться

Користувач затвердив конкретний результат → збережи файл у references/photos/ →
онови відповідний profiles layer у config/photo-styles.json → підвищ version →
додай changes → новий план і перевірка → commit/push або reviewable patch.
categories ключується точною URL UG-OPT, products — selectionKey на кшталт ugopt:123.
families — широка група на кшталт hair-styling. Вибирай найвужчу потрібну область.
Глобальні заборони завжди додаються до спеціальних правил; локальні правила не
повинні їм суперечити. Схвалений вигляд не гарантує однакових пікселів при повторній
генерації: для точного повтору використовуй сам збережений файл після перевірки SKU.

## 6. Стани й відновлення

WAITING_FOR_OPERATOR — поточний етап ще не виконаний. EXPORTED — Excel записаний,
а не імпортований у Prom. Після експорту CLI резервує коди; reservationStatus має
бути COMPLETE. Імпорт у Prom і підтвердження імпорту виконуються окремо.

CLI спочатку зберігає recovery checkpoint із reservationStatus=PENDING. Якщо процес
обірвався між експортом і резервуванням, переглянь цей результат та звір фактичні
резервування через prom-catalog-bootstrap перед новим запуском. Це не транзакція
між файловою системою і SQLite. Не запускай паралельно старий production/scheduler
для тієї самої партії. Lock після аварії видаляй лише перевіривши, що процес завершився.

Зберігай requests/, runtime/ і outputs/ між перезапусками. Вони не мають автоматично
потрапляти в Git. Правила й схвалені еталони, навпаки, мають бути закомічені.
Category CLI підключено до runtime/category-state.sqlite: зберігається результат
кожного товару, прийняті артефакти відновлюються на повторному запуску. Нові
productInputs зливаються по полях, не замінюють цілком збережений товар.
План без п'яти файлів не імпортується як готовий photoArtifact. Джерельні масиви
та часткові фото зберігай у request/окремому progress-файлі, як описано в
CODEX_CATEGORY_EXECUTION.md. Це не обіцянка автономного продовження після
закриття сесії або вичерпання ліміту; відновлення відбувається при наступному запуску.
Завершений export checkpoint не перезаписується: для нової партії потрібен новий result path.
