# Codex виконує задану партію або всю категорію

Це інструкція для агента, який відкрив цей репозиторій. Користувач дає точну
категорію UG-OPT; Codex сам виконує збір, контент, творчий план, генерацію,
перевірку, публікацію зображень і складання Excel. Node-код координує й перевіряє
артефакти. Він не має доступу до вбудованих інструментів чужої ChatGPT-сесії.

## Перший запуск

1. Прочитай AGENTS.md, README.md, config/photo-styles.json і цей документ.
   Відкрий збережений еталон references/photos/global/commercial-infographic-approved-2026-09-17.png.
2. Перевір доступні інструменти: читання сайту, ImageGen, перегляд зображень,
   локальні файли/Node.js 24, доступний хостинг із публічними прямими HTTPS URL.
   Не вимагай API key, якщо доступна вбудована генерація Codex.
3. Для нової партії створи унікальні request/result шляхи. Прочитай збережений
   каталог із config/category-workflow.json; не проси повторно його вказувати.
   Створи requests/<category>.json за examples/category-request.example.json.
   Використай точну URL категорії. Для неоднозначної назви спершу встанови правильну URL.
4. Запусти `npm ci`, потім
   `npm run category -- --request requests/<category>.json --result outputs/<category>-result.json`.
   Усі сторінки категорії проходять збір. Якщо запитана кількість, запиши
   targetCount. Ліміт застосовується лише після звірки кодів та базової придатності.
   Без кількості відбирається вся нова допустима категорія.

## Цикл до готового результату

Читай результат і виконуй усі актуальні operatorTasks. WAITING_FOR_OPERATOR —
черга для Codex, а не вимога ручної роботи користувача. Після додавання артефактів
у productInputs повторюй ту саму команду. Не підмінюй процес окремим генератором Excel.

- Перед контентом відкрий сторінку кожного точного SKU. Збережи ціну, наявність,
  бренд, опис, усі доступні характеристики, справжні фото й походження даних.
  sourceFacts не повинні містити непідтверджені висновки з назви або іншого товару.
  Реальні властивості та відповідність SKU важливіші за рекламну обіцянку.
- CONTENT_GENERATION / CONTENT_REWORK: виконай завдання за його схемою; запиши
  contentArtifact. Продаючі назви, описи й ключі мають пройти чинні перевірки.
  Назва повинна прямо називати призначення товару, коли воно підтверджене
  sourceFacts. Обірвані фрази «для: ...» і загальні слогани замість призначення
  є помилкою CONTENT_REWORK.
- PHOTO_ART_DIRECTION: склади окремий photoCreativeBrief для SKU й запиши його
  у productInputs[productKey].photoCreativeBrief. Схема надана в завданні.
  П'ять різних смислів, сцен, композицій і макетів. Перевір попередні концепції
  в завданні та runtime/photo-creative-history.json; переглянь попередні галереї.
  Сам референс визначає рівень оформлення, а не фіксований бежевий фон.
- PHOTO_GENERATION / PHOTO_REWORK: використовуй саме поточні prompt і plan.
  Передай реальні зображення джерела як identity references, а еталон як style-only.
  Створи п'ять окремих файлів вбудованим ImageGen. Не замінюй генерацію колажем,
  HTML/SVG-карткою, чорним ореолом або копією іншого SKU.
- Перевір кожне фото й усі п'ять разом: товар, написи, факти, фізика використання,
  унікальність сцен і макетів, відмінність від інших товарів. Візуальний огляд
  виконує Codex через перегляд справжніх зображень. Не проставляй true за промптом.
  Кадри 1–4 мають доречну інфографіку; 5 — предметне фото без тексту та піктограм.
- Невдалий кадр перероби окремо, зберігаючи прийняті зображення. Якщо правка
  змінює сам творчий план, отримай новий план і перевір узгодженість усієї серії.

## Приймання готових файлів без платного API

Вбудовані інструменти залишають реальні файли на диску. Збережи робочі копії
в outputs/<category>/photos/<safe-product-key>/ всередині репозиторію, не
перезаписуючи схвалені файли. Для їх перевірки є команда:

```powershell
npm run category:photos -- --input requests/photo-import.json --output outputs/photo-artifact.json
```

photo-import.json містить:

- `plan`: точний поточний products[].photoArtifact.plan з результату category;
- `sourceFacts`: ті самі перевірені факти, що використані під час планування;
- `files`: рівно п'ять записів `{photoIndex, path, sha256}`, де path абсолютний,
  а sha256 відповідає байтам зображення, яке Codex уже переглянув;
- `visualQa`: `{productKey, version, verification: "OPERATOR_CHECKLIST", status,
  photos: [{photoIndex, role, checks}]}` за чинним контрактом photo-quality.mjs.

За відсутності visualQa команда видає REVIEW і готові назви checks зі значенням
false; це корисна схема, але не схвалення. Заповнюй її лише після огляду.
Команда перевіряє PNG, розміри, SHA, дублікати, поточний стиль і checklist;
вона не генерує фото, не здійснює викликів API й не публікує файли.
Не перезаписуй попередній результат імпорту: обери новий output path.
Результат запиши у productInputs[productKey].photoArtifact і повтори category.

## Публікація фото та Excel

MEDIA_PUBLICATION / DRIVE_MEDIA_PUBLICATION виконується через підключений Google Drive.
Папки збережені в config/google-drive-media.json: Prom 2.0 → PRODUCT IMAGES.
Читання папок та запис еталону перевірені 2026-09-17. Успішний upload ще не є
перевіркою прямого URL для Prom. Для Prom
потрібні прямі публічно доступні адреси самих фото. sandbox-посилання, локальний
шлях, сторінка перегляду Drive або тимчасова адреса генератора не є готовою заміною.
Використай чинний google-drive-media-publication bridge і перевірку URL з task.
Після завантаження запиши publication з productKey, sourceCode, folderId та
п'ятьма items: index, role, filename, fileId, sha256, publicUrl. Ролі/імена/хеші
бери з поточного Drive task, ID — зі справжньої відповіді upload. Поруч передай
approvedMedia з поточної Photo QA. Вхід JSON: `{publication, approvedMedia}`.

```powershell
npm run category:media -- --input requests/publication.json --output outputs/publishable-media.json
```

Команда перевіряє завантаження за прямими Google HTTPS URL без cookies/авторизації,
MIME image/* та збіг SHA із локальними схваленими файлами. Сторінка входу, HTML
viewer, змінені байти чи інша папка блокують приймання. Вихід запиши у
productInputs[productKey].publishableMedia і повтори category. Сам CLI не завантажує
файли в Drive: це робить підключений інструмент Codex. Не запускай платний API.
Якщо хостинг ще не підключений, збережи фото й прогрес, назви конкретне блокування;
не вигадуй посилання й не називай Excel готовим до імпорту.

Фінальний Excel створює лише exportPromDeltaWorkbook: еталонні 108 колонок,
поля UA/RU, ціна, код, одиниця, категорія, характеристики й п'ять адрес фото.
Цінова політика залишається чинною category ROI curve; не змінюй її за припущенням.
У магазин Prom нічого не імпортуй без окремого запиту.

## Прогрес, ліміти й повторний запуск

CLI зберігає кожен результат товару у runtime/category-state.sqlite; той самий
request/result відновлює той самий runId. Нові поля запиту перекривають відповідні
збережені поля, не стираючи решту артефактів. Старий план без п'яти зображень не
вважається готовим photoArtifact. Зберігай сам request із джерельними фото.

Після КОЖНОГО згенерованого кадру Codex зберігає локальний файл і оновлює
runtime/photo-progress/<safe-product-key>.json: productKey, версію плану,
style fingerprint, sourceImageRefs, індекс/роль, абсолютний шлях, SHA і стан
огляду. На відновленні перечитай цей файл, перевір SHA/план/стиль та продовжуй
відсутні кадри. Partial progress не передавай як готовий п'ятифайловий артефакт.
Цей покадровий запис виконує агент; CLI сам не спостерігає за ImageGen.

Вхід через ChatGPT і вбудована генерація використовують доступні ліміти плану.
API key означає окрему оплату; не переходь на нього без прямої вказівки.
Не обіцяй фіксовану кількість SKU за тиждень і не обходь ліміти. Якщо виконання
зупинено лімітом, запиши точний останній крок і причину; наступна сесія відновлює
роботу. Сам репозиторій не може гарантувати автоматичний запуск після поновлення ліміту.
Актуальне джерело: https://learn.chatgpt.com/docs/pricing (перевірено 2026-09-17).

## Що вважати завершенням

Потрібні completion.finalWorkbookReady=true та reservationStatus=COMPLETE.
Покажи кількість знайдених, готових, уже наявних/зарезервованих і заблокованих
товарів, готовий XLSX і кількість фото. Для N готових товарів має бути 5N фото.
Невалідні дані, PHOTO_REVIEW, ручне уточнення та непубліковані фото блокують
фінальну категорію. Наявні товари не дублюються; їх оновлення є окремим запитом.

Ці правила й еталон мають бути в тій копії репозиторію, яку відкрив Codex.
ZIP не оновлює GitHub автоматично. Після перенесення змін у справжній checkout
виконай перевірки й commit/push у погоджену гілку.

## Партія із заданою кількістю

Короткий запит «зроби 100 товарів із категорії …» автоматично означає весь
описаний маршрут, включно з перевіркою дублів. Приклад —
examples/category-batch-request.example.json. Codex сам створює JSON; користувач
не повинен редагувати його або нагадувати окремі етапи.

selection.selectedProductKeys фіксує склад партії; CLI відновлює його з result
при продовженні. Зміна порядку карток постачальника не замінює вже вибрані товари.
Зниклий/заблокований вибраний SKU потребує розбору, а не мовчазної заміни результату.
selection.deferredProductKeys — нові товари поза запитаною кількістю.

Для меншої доступної партії можна отримати partialWorkbookReady=true і
INSUFFICIENT_NEW_PRODUCTS із точним shortfall. Це дозволяє передати готові
доступні товари, не видаючи їх за виконані 100. Для повної замовленої партії
потрібні finalWorkbookReady=true, requestedCountMet=true і reservationStatus=COMPLETE.

Конфіг запам'ятовує новий export.inputPath лише після успішного bootstrap.
Змінений експорт із вже створеним реєстром потребує reconciliation; не стирай
історію резервувань. Один проєкт не бачить резервування іншого проєкту автоматично.
