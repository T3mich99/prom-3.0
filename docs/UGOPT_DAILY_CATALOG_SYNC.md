# UG-OPT Daily Catalog Sync and Availability Watch v1

## Purpose

This additive domain produces a deterministic, advisory report for one UG-OPT
catalog observation. It compares an explicitly normalized current snapshot with
an optional trusted previous snapshot, reports availability transitions and
purchase-price changes, and identifies active store products whose supplier
fulfillment is unsafe or uncertain.

The module does not fetch the network, call Prom, change a store product, run
pricing, generate content or photos, or persist state. A scheduler, database,
alerts, and Prom synchronization belong to later reliability work.

## Snapshot contract

`buildUgoptCatalogSnapshot` accepts a caller-provided result from a supplier
adapter:

```js
{
  supplier: 'ug-opt',
  scanId: 'caller-supplied-id', // optional; never generated by the module
  scope: {
    requestedCategoryKeys: ['home', 'tools'],
    completedCategoryKeys: ['home', 'tools'],
    failedCategoryKeys: [],
  },
  complete: true,
  products: [{
    productKey: 'ugopt:F-001',
    supplier: 'ug-opt',
    supplierSku: 'F-001',
    sourceUrl: 'https://ug-opt.in.ua/ua/p-f-001.html',
    availability: 'SELLABLE', // SELLABLE | UNAVAILABLE | UNKNOWN
    purchasePriceMinor: 23000,
    currency: 'UAH',
    categoryKey: 'home',
    provenance: { adapter: 'existing-adapter' },
  }],
}
```

`productKey` is the primary diff identity. The current repository's UG-OPT
adapter already exposes `selectionKey = ugopt:${supplierSku}`; a boundary
mapper may carry that exact opaque key into `productKey`. This module does not
invent another normalization or diff by title, array position, category
position, price, photo, or URL.

The product snapshot rejects duplicate keys, invalid suppliers, invalid UG-OPT
URLs, unsupported currencies, negative or non-integer minor prices, and missing
provenance. Missing price is accepted as an explicitly incomplete observation
so the report can mark a sellable-looking product `AT_RISK`; it is never
converted to zero. `UNKNOWN` availability is retained in the snapshot and
becomes `AT_RISK` in the report.

## Completeness and partial-scan safety

`complete: true` is earned only when the requested scope is non-empty, every
requested category is in `completedCategoryKeys`, and `failedCategoryKeys` is
empty. Completed and failed keys must be inside the requested scope and cannot
overlap. Contradictory metadata is rejected.

Removal requires both snapshots to be trusted and to cover the same exact
scope. A partial, failed, uncovered, zero-product, or scope-mismatched scan
never turns absence into `REMOVED`. Missing products in such a scan are
`AT_RISK` with an `INCOMPLETE_SCAN` diagnostic. A product observed explicitly
as unavailable can still be `UNAVAILABLE` even when an unrelated category
failed.

## States and events

Availability state and transition event are separate:

- `SELLABLE`: trusted current supplier evidence explicitly says the product
  can be fulfilled and its required purchase price is present.
- `UNAVAILABLE`: a successful product observation explicitly says the item
  cannot currently be purchased. It is not inferred from absence.
- `AT_RISK`: evidence is incomplete or conflicting, a product-page/provider
  check failed, availability is `UNKNOWN`, or a required current price is
  missing. Provider failure is never treated as unavailable.
- `REMOVED`: the product was in a trusted previous snapshot and is absent from
  a trusted current snapshot covering the same scope.

The report can emit these events:

- `NEW_SUPPLIER_PRODUCT` after a trusted previous snapshot;
- `PRICE_CHANGED` when both trusted integer minor prices differ;
- `BECAME_UNAVAILABLE` for `SELLABLE` to `UNAVAILABLE`;
- `BACK_IN_STOCK` for `UNAVAILABLE` to `SELLABLE`;
- `REMOVED_FROM_SUPPLIER` for a trusted disappearance;
- `REAPPEARED` when monitor state preserves a prior `REMOVED` state and the
  same key returns in a trusted snapshot;
- `UNCHANGED` for an unchanged trusted observed state.

The first trusted scan sets `baselineCreated: true` and does not emit a new
event for every baseline product. Repeating the same trusted snapshot produces
no new, removal, price, return, or availability-transition delta.

## Price changes and downstream candidates

Prices are compared only as integer `purchasePriceMinor` UAH values. A change
exposes the previous value, current value, absolute integer delta, optional
signed `deltaMinor`, and `requiresRepricing: true`. No commission, delivery, profitability, or selling
price is calculated here. New sellable products, price changes, back-in-stock
products, and reappeared products are exposed as `repricingCandidates`; new
products are also exposed as `newProductCandidates` with
`requiresPricingEvaluation: true`. The PR does not invoke the PR #22 market
researcher and does not publish any pricing decision.

## Active-store fulfillment risk

The comparison accepts provider-neutral injected input:

```js
[{ productKey: 'ugopt:F-001', active: true, storeProductId: 'store-1' }]
```

Duplicate keys are rejected. Inactive products are ignored. An active product
whose supplier state is `UNAVAILABLE` or `REMOVED` is listed once under
`storeRisks.critical` with
`CRITICAL_SUPPLIER_FULFILLMENT_RISK`. An active product whose state is
`AT_RISK`, or which was not observable, is listed under `storeRisks.uncertain`
with `SUPPLIER_STATE_UNCERTAIN`. Uncertainty is never reported as confirmed
unavailability.

## Monitor state

Persistence is out of scope, but the pure `advanceUgoptMonitorState` helper
can carry an explicit in-memory artifact between runs:

```js
{
  supplier: 'ug-opt',
  products: [{
    productKey: 'ugopt:F-001',
    lastKnownSupplierState: 'REMOVED',
    lastKnownPriceMinor: 23000,
  }],
}
```

The comparison accepts this artifact and returns `nextMonitorState`. It keeps
removed keys, which makes `REMOVED` to same-key `REAPPEARED` observable without
pretending that two immediate snapshots alone contain absent-product history.

## API

```js
compareUgoptCatalogSnapshots({
  previousSnapshot,
  currentSnapshot,
  activeStoreProducts,
  monitorState,
})
```

The returned report contains deterministic summary counters, per-product
records, change collections, store-risk collections, diagnostics,
`repricingCandidates`, `newProductCandidates`, and the next monitor state.
Collections are sorted by `productKey`; the input objects are not mutated.
`formatUgoptDailySummary(report)` provides a deterministic Ukrainian text
summary for a later alert transport.

## Current integration boundary

The existing adapter remains category-scoped and exposes explicit HTTP,
network, and parse failures, but it does not currently provide a product-level
availability field. The new domain therefore does not reimplement scraping.
An eventual retrieval layer must map proven adapter/page observations to the
snapshot contract, use the existing opaque product identity, and mark failed
product observations with `UNKNOWN` plus a provider-failure observation.
Completeness must be supplied from actual requested/completed/failed scope
coverage, never inferred from a non-empty array.
